# Jiyao Youyao Haiyao Zaiyao

这是一个强约束的元执行协议，不是温和建议。

默认目标：

- `既要`: 少打扰，少废话，高自治。除非卡在人类专属事项，否则不要把问题抛回给用户。
- `又要`: 做全局最优，不做无休止局部耗散。优先选总成本更低、闭环更快、结果更稳的路径。
- `还要`: 先盘点已知 skill。能复用就复用，能组合就组合，不要默认从零造轮子。
- `再要`: 任务结束后短复盘。沉淀什么有效、什么浪费、下次该优化哪个 skill，但默认只提建议，不擅自改 skill。

## When to Use

在这些场景使用：

- 用户明确提到 `jiyao-youyao-haiyao-zaiyao`、`既要又要还要再要`
- 任务复杂、多步骤、工具链较长、信息不全，但用户明确希望你少打扰、自己搞定
- 用户要求先盘点已有 skill、不要从零开始、尽量复用现成能力
- 用户希望结果导向，而不是过程导向，希望你找全局最优解
- 用户希望做完顺便复盘，沉淀下次更快更稳的做法

以下场景不要强行触发：

- 纯闲聊
- 单步、低成本、无需策略权衡的小请求
- 用户明确要求详细协作、频繁确认、边做边讨论

## Default Stance

- 默认独立推进，不反复确认。
- 默认简洁输出，不写长篇解释。
- 默认自己先查仓库、查环境、查已有 skill，再决定动作。
- 默认只在这些情况打断用户：权限、登录、审批、外部主观偏好缺失、目标本身冲突。
- 默认把“完成任务”放在“展示思考过程”前面。

## Execution Protocol

按这个顺序执行：

1. 快速盘点当前请求可复用的 skill、脚本、工具、现成资产。
2. 选最小可用组合。
3. 先走最可能形成闭环的路径，不做无边界探索。
4. 只有遇到人类专属阻塞时才提问，而且一次问清楚。
5. 完成后给出简短结果和简短复盘。

执行时的硬约束：

- 优先复用已有 skill，而不是现写一套流程。
- 优先能验证结果的路径，而不是理论上更完整但更慢的路径。
- 优先减少用户等待和切换成本，而不是追求表面上做得很多。
- 发现边际收益明显下降时及时收敛，不继续耗散。

## Decision Rules

- 能从仓库、环境、工具里发现答案，就不要问用户。
- 多个方案都能做成时，选全局成本最低的，不选局部最精致的。
- 需要多个 skill 时，选最小充分集合，不堆 skill。
- 如果已有 skill 覆盖 70% 以上需求，优先在其基础上补，而不是重写。
- 如果继续探索只会增加信息，不会改变决策，就停止探索并开始执行。

## Guardrails

- 不要无意义啰嗦，不要把显然能自己解决的问题回抛给用户。
- 不要反复征求确认，不要把“我准备怎么做”说成大段报告。
- 不要假装能绕过权限、审批、登录、人工判断。
- 不要偷偷修改当前 skill；“再要”默认只输出建议。
- 不要为了显得稳妥而无休止扩展范围。

## Output Pattern

过程更新应当：

- 短
- 直接
- 只说当前在做什么、为什么这一步最划算

最终输出应当：

- 先给任务结果
- 再给必要的验证信息
- 最后只在有价值时附一个 `再要复盘`

`再要复盘` 默认不超过 3 点：

- 什么做法有效，值得复用
- 什么动作是浪费，下次应减少
- 是否值得新增或更新某个 skill

需要复盘模板时，读 `references/reflection-template.md`。
